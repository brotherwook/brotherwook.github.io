## 스트림에는 경계가 없다

장비 통신을 붙이다 보면 STX/ETX/DLE/CRC 조합을 계속 만나게 된다. 매번 어렴풋이 알고 넘어가다가 이번에 제대로 걸려서.. 다음의 나를 위해 정리해둔다.

시리얼(RS-232/485)이든 TCP 소켓이든, 내가 받는 건 결국 **바이트가 줄줄이 흘러오는 스트림**이다. 여기엔 "여기까지가 한 메시지"라는 경계가 없다. 송신 측이 100바이트짜리 패킷 하나를 보내도, 수신 측에서는 40바이트 읽히고 나머지 60바이트가 다음 `read()`에서 들어오기도 하고, 반대로 두 패킷이 한 번에 붙어서 오기도 한다.

그래서 애플리케이션이 직접 **프레이밍(framing)** 을 해야 한다. 흘러오는 바이트 더미에서 "어디부터 어디까지가 한 프레임인지"를 잘라내는 규칙이다. STX/ETX/DLE/CRC는 그 프레이밍을 하는 가장 고전적인 방법인데, 각 조각이 서로 다른 문제를 푼다. 하나씩 보자.

## STX / ETX — 프레임을 문자로 감싼다

가장 단순한 발상은 "특별한 문자로 시작과 끝을 표시하자"는 것이다. ASCII 제어 문자 중에 이 용도로 정해진 게 있다.

- **STX (Start of Text, `0x02`)** — 프레임 시작. 수신 측은 이 바이트를 만나면 "여기서부터 데이터가 시작된다"고 판단한다.
- **ETX (End of Text, `0x03`)** — 프레임 끝. STX와 ETX 사이가 실제 데이터 영역이 된다.

수신 로직은 대충 이런 상태 기계가 된다.

```
IDLE 상태에서 바이트를 계속 버리다가 → STX를 만나면 RECV 상태로
RECV 상태에서 바이트를 버퍼에 쌓다가 → ETX를 만나면 프레임 완성
```

개념 예제로 쓰면 이 정도다.

```python
STX, ETX = 0x02, 0x03

def frame_reader(stream):
    buf = bytearray()
    in_frame = False
    for byte in stream:            # 스트림에서 1바이트씩
        if not in_frame:
            if byte == STX:
                in_frame = True
                buf.clear()
        else:
            if byte == ETX:
                yield bytes(buf)   # 한 프레임 완성
                in_frame = False
            else:
                buf.append(byte)
```

깔끔해 보인다. 그런데 여기엔 치명적인 문제가 하나 숨어 있다.

## DLE — 데이터가 STX/ETX 흉내를 낼 때

만약 **데이터 안에 `0x03`(ETX와 같은 값)이 들어있으면** 어떻게 될까. 위 로직은 그걸 진짜 프레임 끝으로 오인하고 거기서 프레임을 잘라버린다. 텍스트만 주고받을 땐 제어 문자가 데이터에 안 섞이니 괜찮지만, 바이너리 데이터(센서 값, 좌표, 길이 필드 등)를 보내는 순간 `0x02`, `0x03` 같은 값은 얼마든지 자연스럽게 등장한다.

이걸 해결하는 게 **DLE (Data Link Escape, `0x10`)** 다. 발상은 프로그래밍 언어의 escape 문자(`\`)와 똑같다. "다음에 오는 바이트는 제어 문자가 아니라 그냥 데이터로 취급하라"는 표시다.

규칙은 이렇다. 송신할 때 데이터 바이트가 STX/ETX/DLE 중 하나와 같은 값이면, 그 앞에 DLE를 하나 끼워넣는다. 이걸 **바이트 스터핑(byte stuffing)** 혹은 DLE stuffing이라고 부른다.

| 데이터에 이 값이 있으면 | 이렇게 전송 |
|---|---|
| `0x02` (STX와 같음) | `DLE 0x02` |
| `0x03` (ETX와 같음) | `DLE 0x03` |
| `0x10` (DLE 자기 자신) | `DLE DLE` |

DLE 자신도 반드시 escape해야 한다는 게 포인트다. 안 그러면 데이터에 우연히 들어간 `0x10`을 수신 측이 "다음 바이트를 escape하라"는 신호로 착각한다.

프레임 경계를 나타내는 STX/ETX도 `DLE STX`, `DLE ETX` 쌍으로 표현하는 변형도 흔하다. 이렇게 하면 "escape 안 된 홑 DLE STX"만이 진짜 프레임 시작이 되어 경계가 더 명확해진다.

송신 측 스터핑을 개념 코드로 쓰면:

```python
STX, ETX, DLE = 0x02, 0x03, 0x10
SPECIAL = {STX, ETX, DLE}

def stuff(data: bytes) -> bytes:
    out = bytearray([STX])
    for b in data:
        if b in SPECIAL:
            out.append(DLE)     # escape 삽입
        out.append(b)
    out.append(ETX)
    return bytes(out)
```

수신 측은 반대로, DLE를 만나면 "다음 1바이트는 무조건 데이터"로 처리하고 DLE 자체는 버린다(unstuffing).

```python
def unstuff(frame_body):
    out = bytearray()
    escaped = False
    for b in frame_body:
        if escaped:
            out.append(b)       # DLE 다음 바이트는 그대로 데이터
            escaped = False
        elif b == DLE:
            escaped = True      # DLE는 버리고 다음 바이트를 기다림
        else:
            out.append(b)
    return bytes(out)
```

이걸로 데이터에 어떤 바이트가 들어오든 프레임 경계가 깨지지 않는다.

> 참고로 프레임 경계를 문자로 표시하는 방식 말고, **길이 접두(length-prefix)** 방식도 있다. 헤더에 "이 프레임의 길이는 N바이트"라고 박아두고 그만큼 읽는 것. 이 경우 데이터에 제어 문자가 섞여도 상관없어서 스터핑이 필요 없다. 대신 길이 필드가 깨지면 동기화 복구가 까다롭다. STX/ETX+DLE 방식은 경계 문자를 보고 언제든 재동기화할 수 있다는 게 장점이라, 노이즈가 낀 시리얼 환경에서 특히 선호된다. 실무에서는 둘을 섞어 `STX | LENGTH | DATA | CRC | ETX` 처럼 쓰기도 한다.

## CRC — 내용이 안 깨졌는지 검증한다

프레임 경계를 제대로 잘라냈다고 해서 끝이 아니다. 전송 도중 비트가 뒤집혔을 수 있다(전기적 노이즈, 케이블 불량 등). 그래서 **데이터가 손상되지 않았는지 검증**하는 값이 필요한데, 그게 **CRC (Cyclic Redundancy Check)** 다.

원리는 이렇다. 데이터를 하나의 큰 이진수로 보고, 미리 약속한 **생성 다항식(generator polynomial)** 으로 나눗셈(정확히는 GF(2) 위의 다항식 나눗셈, 실제로는 XOR 시프트)을 해서 나온 **나머지**를 CRC 값으로 삼는다. 송신 측이 이 값을 프레임에 붙여 보내고, 수신 측이 받은 데이터로 똑같이 계산해서 값이 일치하는지 확인한다. 하나라도 다르면 프레임을 버리고 재전송을 요청한다. (다항식 나눗셈 부분은 솔직히 나도 수학적으로 깊이 파진 않았다.. 라이브러리를 쓰는 입장에선 "약속한 파라미터로 나머지를 구한다" 정도로 이해해도 충분했다.)

단순히 바이트를 다 더하는 **체크섬(checksum)** 도 오류 검출용이지만, CRC가 훨씬 강하다. 체크섬은 두 바이트가 서로 상쇄되게 뒤집히면 못 잡지만, CRC는 다항식 특성상 그런 패턴에도 강하고 특히 **연속된 비트 오류(burst error)** 검출력이 좋다. 시리얼/필드버스 환경에서 CRC가 표준처럼 쓰이는 이유다.

자주 보게 되는 종류:

- **CRC-8** — 짧은 프레임, 저사양 MCU에서.
- **CRC-16** — Modbus RTU, 각종 산업용 시리얼 프로토콜의 단골. CCITT 변형(`0x1021` 다항식)도 자주 쓰인다.
- **CRC-32** — Ethernet, ZIP, PNG 등. 더 긴 데이터에.

CRC는 직접 구현하기보다 검증된 라이브러리나 표준 구현을 쓰는 걸 권한다. 다만 프로토콜 문서를 볼 때 **파라미터**를 반드시 맞춰야 한다. 같은 "CRC-16"이라도 다항식(polynomial), 초기값(init), 입력·출력 비트 반전(reflect in/out), 최종 XOR 값이 다르면 결과가 완전히 달라진다. 상대 장비와 값이 안 맞으면 십중팔구 이 파라미터가 틀린 것이다.. 나도 여기서 "코드는 맞는데 값이 안 맞네" 하고 한참 헤맸다.

Python이라면 `crcmod`나 `binascii.crc32` 같은 걸 쓰면 된다. 개념만 보이면:

```python
import crcmod
# 예: CRC-16/CCITT-FALSE 파라미터 (장비 스펙에 맞게 지정)
crc16 = crcmod.mkCrcFun(0x11021, initCrc=0xFFFF, rev=False, xorOut=0x0000)
value = crc16(b"payload bytes")   # 이 값을 프레임에 붙여 전송
```

## 다 합치면 하나의 프레임

정리하면 전형적인 프레임은 대략 이런 모양이 된다.

```
STX │ (LENGTH) │ DATA (byte-stuffed) │ CRC │ ETX
```

- **STX/ETX**: 어디가 시작이고 끝인지 — 경계.
- **DLE 스터핑**: 데이터가 경계 문자를 흉내 내지 못하게 — 투명성(transparency).
- **CRC**: 잘라낸 내용이 안 깨졌는지 — 무결성.

세 가지가 각각 다른 문제를 푼다. 경계, 투명성, 무결성. 이걸 헷갈리면 "CRC 넣었으니 됐지" 하고 스터핑을 빼먹었다가, 데이터에 `0x03` 섞이는 순간 프레임이 반토막 나는 걸 겪게 된다.. 경험담이다.

## 실무에서 자주 걸리는 지점

문서 볼 때 나는 이것들부터 확인한다.

1. **CRC 계산 범위** — STX/ETX를 포함하는지, LENGTH 필드는 포함하는지, DATA만인지. 프로토콜마다 제각각이다.
2. **스터핑과 CRC의 순서** — 보통 CRC를 먼저 계산하고 그 다음에 전체를(CRC 포함) 스터핑한다. 즉 수신 측은 unstuff → CRC 검증 순서. 순서를 반대로 하면 절대 값이 안 맞는다.
3. **CRC 바이트 순서(엔디안)** — CRC-16을 붙일 때 상위 바이트 먼저인지 하위 먼저인지. Modbus는 하위 바이트 먼저다.
4. **STX/ETX 자체를 스터핑 대상에 넣는지** — 경계 문자를 `DLE STX`로 표현하는 변형이면 계산이 또 달라진다.

결국 이 방식들은 개념은 단순한데, **"이 프로토콜은 정확히 어느 변형이냐"** 를 스펙 문서에서 못 박는 게 90%다. 반대로 말하면, 개념만 잡혀 있으면 문서의 어느 항목을 확인해야 하는지가 보인다는 것.. 그게 이 글의 요점이다.
