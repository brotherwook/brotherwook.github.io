왜 RTSP를 그냥 쓰면 안 됐나#

IP 카메라 영상을 받아올 때 제일 흔히 쓰는 게 RTSP(Real-Time Streaming Protocol)다. 그동안 나도 별생각 없이 써왔는데, 이번에 보안 요건이 걸리면서 한 가지 사실을 마주했다. 표준 RTSP에는 요즘 당연하게 여기는 게 하나 빠져 있다. 전송 구간 암호화다.

RTSP 자체는 스트림을 “제어"하는 프로토콜이다. DESCRIBE, OPTIONS, SETUP, PLAY 같은 명령을 주고받아 세션을 열고, 실제 영상은 RTP로 흘려보낸다. 문제는 이 제어 채널과 인증 정보가 기본적으로 평문으로 오간다는 것.. 카메라 계정 자격증명이 네트워크에 그대로 노출될 수 있고, 중간자 공격에도 취약하다.

평소엔 넘어갈 수 있어도, 제품이 보안 인증(전송 구간 암호화 여부를 보는 항목)을 통과해야 하는 상황이면 평문 RTSP는 선택지가 아니다. 그래서 RTSP 세션 전체를 TLS 위에 얹는 방식, URL 스킴으로는 rtsps:// 라 부르는 방식을 쓰게 됐다. HTTP가 HTTPS 되는 거랑 정확히 같은 발상이다. TCP로 열던 소켓을, TLS 핸드셰이크 먼저 하고 그 위에서 RTSP 메시지를 주고받게 바꾸는 것.

개념은 이렇게 간단하다. “TLS 소켓 위에서 하던 RTSP 그대로 하면 되는 거 아냐?” 맞다. 그런데 라이브러리에 안 기대고 직접 구현하려니 생각보다 걸리는 데가 많았다. 아래는 막혔던 지점을 순서대로 적어둔 것이다. 나처럼 직접 짜야 하는 상황이 아니라면 그냥 성숙한 라이브러리를 쓰는 걸 추천한다.. 이건 어디까지나 “직접 해봐야 했던” 기록이다.

1. TLS 소켓 위에서 요청 보내기 — SSL 에러의 늪#

Python으로 TLS 소켓 열고 그 위로 요청 보내는 것 자체는 ssl 모듈로 쉬워 보였다. 실제로는 SSL 에러부터 꽤 만났다.

전형적으로 만나는 것들:

  • 인증서 검증 실패 — 카메라·장비는 자체 서명(self-signed) 인증서를 쓰는 경우가 많다. 기본 검증 모드에서는 CERTIFICATE_VERIFY_FAILED가 뜬다. 신뢰할 수 있는 내부망 장비라는 전제가 있다면 검증 모드를 조정하거나 인증서를 신뢰 목록에 넣어야 한다.
  • 호스트네임 불일치 — 인증서의 CN/SAN과 접속 IP가 안 맞을 때. check_hostname과 충돌한다.
  • 프로토콜/사이퍼 협상 실패 — 장비가 오래된 TLS 버전이나 특정 사이퍼만 받을 때.

대략 이런 뼈대였다. (실제 서비스 코드가 아니라 개념용 예제다.)

import socket
import ssl

context = ssl.create_default_context()
# 자체 서명 인증서를 쓰는 내부망 장비 대상: 검증 정책은 환경에 맞게 결정
context.check_hostname = False
context.verify_mode = ssl.CERT_NONE  # 신뢰된 폐쇄망 전제일 때의 선택. 공개망이면 이렇게 하면 안 된다.

raw = socket.create_connection((host, port), timeout=5)
tls = context.wrap_socket(raw, server_hostname=host)

# 이제 tls 소켓 위로 RTSP 텍스트 메시지를 write/read 하면 된다
tls.sendall(request_bytes)
data = tls.recv(4096)

여기서 배운 것.. verify_mode를 끄는 건 “폐쇄망 + 장비 신뢰"라는 전제가 명확할 때의 트레이드오프다. 왜 껐는지 근거를 안 남기면 나중에 보안 관점에서 지적받기 딱 좋은 부분이라, 결정 이유를 주석과 문서로 남기는 게 맞다.

2. Digest 인증 직접 만들기 — RFC 7616 읽기#

TLS 소켓이 열리면 다음은 인증이다. RTSP는 HTTP의 인증 방식을 그대로 가져다 쓴다. 카메라에 명령을 처음 보내면 401 Unauthorized와 함께 WWW-Authenticate 헤더가 오고, 여기에 Digest 인증에 필요한 파라미터(realm, nonce, qop, algorithm 등)가 들어 있다.

Basic 인증이면 base64(user:pass)로 끝인데, 보안상 Digest(특히 SHA-256)를 요구하는 경우가 있다. 이때 봐야 하는 문서가 **RFC 7616 (HTTP Digest Access Authentication)**이다. 여기 명세대로 응답 해시를 만들어야 한다.

핵심 계산 흐름은 이렇다 (algorithm=SHA-256 기준):

1
2
3

HA1 = SHA256(username : realm : password)
HA2 = SHA256(method : digestURI)
response = SHA256(HA1 : nonce : nc : cnonce : qop : HA2)
  • method는 RTSP 메서드(OPTIONS, DESCRIBE, PLAY 등)
  • nc(nonce count), cnonce(client nonce)는 qop=auth일 때 포함
  • 이 response를 다시 Authorization 헤더에 규격대로 조립해서 보낸다

직접 만들 때 헷갈렸던 건, MD5 시절 예제가 인터넷에 훨씬 많아서 SHA-256으로 바꿀 때 어디까지 그대로 두고 어디를 고쳐야 하는지였다. 결론은 해시 함수만 교체하면 구조는 동일하다. 그리고 algorithm이 SHA-256인지 SHA-256-sess인지에 따라 HA1 계산이 달라지니 서버가 보낸 값을 그대로 따라야 한다.

하나 더 — 요청마다 CSeq를 1씩 올려 보내야 하고, 인증이 필요한 모든 후속 명령에 Authorization을 계속 붙여야 한다. 한 번 인증했다고 세션이 자동으로 유지되는 게 아니다.

3. 명령을 “어디에” 실어야 하나 — 헤더냐 바디냐#

여기서 개념적으로 한참 헤맸다. 인증을 통과한 뒤 OPTIONS, DESCRIBE, SETUP, PLAY를 보내는데, 이걸 HTTP처럼 바디에 넣는 건지, 헤더에 넣는 건지, 아예 다른 형식인지가 처음엔 감이 안 왔다.

정리하고 나니 답은 명확했다. RTSP 메시지는 HTTP와 아주 닮은 텍스트 기반 요청/응답 구조다.

1
2
3
4

PLAY rtsp://.../stream RTSP/1.0
CSeq: 4
Session: 12345678
Authorization: Digest username="...", realm="...", ...
  • 첫 줄이 요청 라인: <메서드> <URI> RTSP/1.0
  • 그 아래로 헤더들 (CSeq, Session, Authorization, 필요시 Range 등)
  • 헤더 끝은 빈 줄(\r\n\r\n)로 구분
  • 대부분의 제어 명령은 바디가 없다. 대상과 옵션은 요청 라인과 헤더로 표현된다

즉 “명령을 바디에 넣는다"는 발상 자체가 틀렸던 것.. 메서드가 곧 명령이고, 세부 옵션은 헤더로 간다. 바디(SDP 등)가 등장하는 건 DESCRIBE의 응답이나 ANNOUNCE 같은 특정 경우다. 이 구조를 이해하고 나서는 메시지 조립이 훨씬 수월해졌다.

4. PLAY 이후 데이터 파싱 — RFC 2326과 Wireshark#

PLAY를 보내면 이제 실제 미디어(RTP로 감싼 H.264 스트림)가 흘러 들어온다. 그런데 이걸 어떻게 잘라 읽어야 하는지가 또 벽이었다.

TCP 인터리브 모드에서는 제어 응답과 미디어 데이터가 같은 연결 위에 섞여서 온다. 이걸 구분하는 규칙이 **RFC 2326의 10.12절 (Embedded (Interleaved) Binary Data)**에 있다.

핵심은 미디어 데이터 앞에 붙는 4바이트 헤더다.

1

$ (0x24) | channel(1 byte) | length(2 bytes, big-endian)
  • 0x24($)로 시작하면 그 뒤는 인터리브된 바이너리 데이터라는 신호
  • 다음 1바이트는 채널 ID
  • 그다음 2바이트가 뒤따르는 데이터 길이

이 규칙을 알기 전엔 바이트 스트림이 그냥 뭉텅이로 보여서 어디서 끊어야 할지 몰랐다. Wireshark로 실제 패킷을 뜯어보면서 $ 마커와 length 필드를 눈으로 확인하고 나서야 파서를 제대로 짤 수 있었다. RFC 문서만으로 이해가 안 되던 게, 실제 패킷과 대조하니 한 번에 잡혔다.

이어붙이기 — length만큼 안 왔을 때#

실무에서 중요한 함정이 하나 더 있다. 헤더에 적힌 length만큼 데이터가 한 번에 안 오는 경우다.

TCP는 스트림이라 “메시지 경계"를 보장하지 않는다. length가 1400바이트라고 적혀 있어도 recv() 한 번에 900바이트만 올 수 있다. 이걸 모르고 한 번 읽은 걸 한 프레임으로 처리하면 데이터가 깨진다.

그래서 파서는 이렇게 동작해야 한다.

  1. 4바이트 헤더를 읽어 length 확인
  2. 버퍼에 length만큼 쌓일 때까지 계속 recv() 해서 이어붙이기
  3. 다 모이면 그 덩어리를 한 단위(RTP 패킷)로 넘기고, 남은 바이트는 다음 파싱을 위해 버퍼에 보관

이것도 Wireshark로 “한 length가 여러 TCP 세그먼트에 걸쳐 오는” 걸 직접 보고 나서야 확신을 갖고 구현했다. 패킷 분석 없이 코드만 봤으면 “가끔 영상이 깨지는” 원인을 한참 못 찾았을 거다.

정리#

라이브러리 하나면 될 걸 왜 직접 했나 싶지만, 이 과정에서 얻은 게 컸다.

  • RTSP over TLS는 “HTTPS와 같은 발상"이지만, 자체 서명 인증서·사이퍼 협상 때문에 소켓 레벨에서 손볼 게 있다.
  • **Digest 인증(RFC 7616)**은 해시 함수만 바꾸면 구조가 같고, 요청마다 CSeq·Authorization을 계속 관리해야 한다.
  • RTSP 제어 명령은 HTTP 유사 텍스트 구조라 메서드가 곧 명령, 옵션은 헤더. 대부분 바디가 없다.
  • 인터리브 스트림 파싱은 RFC 2326 10.12절의 $+channel+length 규칙을 따르고, TCP 특성상 length만큼 이어붙이는 로직이 필수다.

무엇보다 이번 삽질의 진짜 수확은 RFC를 읽고 Wireshark로 실제 패킷과 대조하는 습관이었다. 명세만으로 안 잡히던 게 패킷을 보면 잡혔고, 반대로 패킷만 봐선 헷갈리던 게 명세를 보면 정리됐다. 저수준 프로토콜을 다룰 땐 이 둘을 오가는 게 제일 확실한 길인 것 같다.
