왜 파티셔닝을 보게 됐나#

로그·이벤트처럼 계속 쌓이기만 하는 테이블이 있으면, 언젠가 “이거 너무 커졌는데..” 하는 순간이 온다. 조회도 느려지고, 오래된 데이터 지우자니 DELETE가 한참 걸리고 락도 무섭다. 이때 꺼내는 카드가 파티셔닝이다. 테이블을 논리적으로 한 덩어리로 두되, 내부적으로는 구간별로 잘라 저장해서 “특정 구간만 빠르게 조회하거나 통째로 버리는” 걸 가능하게 하는 것.

개념은 쉬운데 막상 하려니 규칙과 함정이 제법 있었다. 겪은 순서대로 정리해둔다. (MySQL/MariaDB 기준)

규칙 하나만 기억하면 된다 — 파티션 키는 PK에 포함돼야 한다#

파티셔닝의 가장 중요한 규칙은 이거 하나다.

파티션 키로 쓰는 컬럼은 테이블의 모든 UNIQUE/PRIMARY KEY에 포함되어야 한다.

seq(auto_increment)가 PK인 테이블을 seq 기준으로 나누는 건, 이 조건을 이미 만족하니 바로 된다. auto_increment는 값이 단조 증가라 RANGE 파티셔닝의 교과서 같은 후보다.

CREATE TABLE event_log (
    seq     BIGINT NOT NULL AUTO_INCREMENT,
    channel INT,
    reg_dt  DATETIME,
    PRIMARY KEY (seq)
)
PARTITION BY RANGE (seq) (
    PARTITION p0   VALUES LESS THAN (1000000),
    PARTITION p1   VALUES LESS THAN (2000000),
    PARTITION pmax VALUES LESS THAN MAXVALUE   -- catch-all 반드시
);

seq로 나눌까, 날짜로 나눌까#

여기서 한 번 고민하게 된다. 결론부터 말하면 “무엇을 기준으로 데이터를 지울 거냐"로 정하면 된다.

  • 그냥 오래된 것부터 순서대로 비우면 되면 → seq 기준. PK라 조건도 이미 충족하고 관리가 단순하다.
  • “30일/6개월 지난 데이터 삭제” 같은 보관정책이 있으면 → 날짜 기준. 개인적으로 보관정책이 있으면 무조건 날짜 기준을 추천한다. 나중에 DROP PARTITION 한 줄로 기간별로 버릴 수 있어서 훨씬 편하다.

문제는 날짜로 나누려면 날짜 컬럼도 PK에 들어가야 한다는 것. “그럼 날짜 컬럼이 유일하지 않은데 PK가 되나?” 싶었는데, 여기서 헷갈리기 쉬운 포인트가 하나 있다.

복합 PK는 “컬럼 조합"이 유일하면 된다. 각 컬럼이 개별적으로 유일할 필요는 없다.

server_processing_time이 초 단위로 겹쳐도, seq가 auto_increment라 항상 다르니 (seq, server_processing_time) 조합은 100% 유일하다. 그러니 복합 PK로 묶는 데 아무 지장이 없다.

CREATE TABLE image (
    seq                    BIGINT NOT NULL AUTO_INCREMENT,
    server_processing_time DATETIME NOT NULL,
    channel                INT,
    PRIMARY KEY (seq, server_processing_time)     -- 둘 다 포함
)
PARTITION BY RANGE COLUMNS (server_processing_time) (
    PARTITION p2026q1 VALUES LESS THAN ('2026-04-01 00:00:00'),
    PARTITION p2026q2 VALUES LESS THAN ('2026-07-01 00:00:00'),
    PARTITION pmax    VALUES LESS THAN (MAXVALUE)
);

참고로 TO_DAYS() 같은 함수 대신 RANGE COLUMNS 로 DATETIME을 직접 비교하면 VALUES LESS THAN ('2026-04-01 ...')처럼 읽혀서 훨씬 가독성이 좋다. 나는 이 방식을 선호한다.

auto_increment PK를 바꿀 때 걸리는 것#

기존 테이블(seq 단독 PK)을 복합 PK로 바꾸려고 DROP PRIMARY KEY 부터 날리면 이런 에러가 난다.

1

Incorrect table definition; there can be only one auto column and it must be defined as a key

auto_increment 컬럼은 항상 키의 일부여야 하는데, PK를 먼저 떼는 순간 seq가 키에서 빠져버리기 때문이다. 그래서 한 ALTER 문에 DROP과 ADD를 묶어서 seq가 잠깐도 키에서 벗어나지 않게 해야 한다.

1
2
3
4

ALTER TABLE image
    MODIFY server_processing_time DATETIME NOT NULL,   -- PK 구성 컬럼은 NOT NULL 필수
    DROP PRIMARY KEY,
    ADD PRIMARY KEY (seq, server_processing_time);
  • PK에 들어가는 컬럼은 NOT NULL 이어야 한다. 그래서 MODIFY ... NOT NULL이 필요한데, 기존 데이터에 NULL이 있으면 이 문장에서 실패한다. 실행 전에 SELECT COUNT(*) FROM image WHERE server_processing_time IS NULL; 로 꼭 확인.

첫 파티션은 과거 데이터를 다 빨아들인다#

이것도 모르면 당황한다. RANGE에서 첫 파티션은 하한이 없다. VALUES LESS THAN만 있고 “그 이상"이라는 조건이 없어서, 지정한 시작보다 오래된 데이터가 전부 첫 파티션 한 곳에 몰린다.

데이터 날짜들어가는 파티션 (start=2026)
2019-03-15첫 파티션
2022-11-01첫 파티션
2026-02-10첫 파티션
2026-08-20그 다음 파티션

데이터 유실은 없지만(그래서 pmax catch-all이 있는 것), 과거 데이터가 많으면 첫 파티션만 비대해져서 그 구간에선 파티셔닝 이점이 사라진다. 나는 실제 데이터의 시작 시점을 SELECT MIN(...) 으로 확인해서 start를 거기에 맞추거나, 맨 앞에 p_old VALUES LESS THAN ('2026-01-01') 같은 과거 전용 파티션을 하나 두는 쪽으로 처리했다.

실제로 데인 함정들#

여기부턴 솔직한 삽질 기록이다.

① 파티션 테이블은 외래키(FK)를 아예 지원 안 한다. 이게 제일 크다. 파티셔닝하려는 테이블이 FK를 갖고 있거나 다른 테이블에서 FK로 참조되면, PARTITION BY에서 그냥 실패한다. 파티셔닝 전에 SHOW CREATE TABLE로 FK부터 확인해야 한다. 이거 모르고 진행했다가 막판에 걸리면 설계부터 다시 봐야 한다..

② DDL은 롤백이 안 된다. 나는 스크립트에 “실패하면 전체 롤백” 로직을 넣어놨었는데, 알고 보니 **MySQL/MariaDB에서 ALTER TABLE 같은 DDL은 암묵적 커밋(implicit commit)**이 일어난다. 즉 트랜잭션으로 못 묶는다. PK 변경(문장1)이 성공하고 파티셔닝(문장2)이 FK 때문에 실패하면 → PK는 이미 바뀐 채로 남는다. “롤백되겠지” 믿고 있으면 안 된다.

③ 대용량이면 이 ALTER는 테이블 재구성(rebuild)이다. 오래 걸리고 락이 걸리고, 재구성 중엔 원본의 약 2배 디스크 공간이 필요하다. 운영 중인 큰 테이블이라면 pt-online-schema-change(Percona) 같은 온라인 스키마 변경 도구나 점검 시간대 적용을 권한다.

④ 운영 중에 하면 진짜로 테이블이 깨질 수 있다. 이게 제일 크게 데인 부분이다. 파이썬 스크립트로 운영 중인 MariaDB 테이블을 파티셔닝하다가 테이블이 깨진 적이 있다. 정확한 메커니즘은 나도 확신은 못 하는데, 파티셔닝(테이블 재구성)이 도는 도중에 다른 프로그램들이 같은 테이블에 계속 SELECT/INSERT/UPDATE를 하고 있던 것이 원인으로 추정된다. 복구는 어찌어찌 했지만.. 그다음부터는 그 DB를 쓰는 프로그램을 전부 멈춘 뒤에 파티셔닝을 돌렸고, 그렇게 하니 한 번도 안 깨졌다. 교과서적으로는 InnoDB가 알아서 락을 잡아준다지만, 현실에서 살아있는 대용량 테이블을 라이브로 재구성하는 건 그냥 위험한 작업이라고 몸으로 배웠다. 가능하면 접근을 다 끊고(점검 시간대), 그게 안 되면 최소한 온라인 스키마 변경 도구로.

진짜 목적지 — DROP PARTITION 보관정책#

여기까지 감수하고 파티셔닝하는 이유의 8할은 이거다. 오래된 데이터를 지울 때 DELETE는 행을 하나씩 지우며 락·언두로그를 잔뜩 쓰지만, 파티션은 통째로 버리면 끝이다.

1
2

-- "이 구간 데이터 싹 정리" — 거의 즉시, 락 부담 없음
ALTER TABLE image DROP PARTITION p2026q1;

DELETE FROM image WHERE server_processing_time < ... 로 몇 분씩 갈던 게 DROP PARTITION 한 줄로 순식간에 끝난다. 보관정책이 있는 로그성 테이블이라면 이 하나만으로도 파티셔닝할 값어치가 있다.

실행 전 체크리스트#

DDL이 롤백이 안 되는 만큼, 큰 테이블에 적용하기 전엔 이 정도는 보고 들어간다.

  1. 백업 — mysqldump db image video > backup.sql. 이건 그냥 무조건.
  2. DB 쓰는 프로그램 전부 정지 — 위에서 데인 그거. 운영 중 라이브 재구성은 테이블을 깨먹은 적이 있다. 접근을 끊고(점검 시간대) 진행.
  3. 복사본에서 먼저 — 운영 테이블 말고 복제본에 적용해보기.
  4. FK 확인 — 하나라도 있으면 파티셔닝 불가. 설계부터 재검토.
  5. NULL 확인 — PK 될 컬럼에 NULL 있으면 NOT NULL 변환에서 실패.
  6. 건수·디스크 — 대용량이면 락·시간·2배 공간 각오, 온라인 도구 검토.

MariaDB엔 자동 파티셔닝이 없다 — 그래서 나는 미리 만들어둔다#

이렇게 라이브 ALTER가 위험하다 보니, 애초에 그 위험한 작업을 안 하는 게 최선이다. 여기서 DB마다 차이가 하나 있다.

  • Oracle엔 인터벌 파티셔닝(interval partitioning)이 있어서, 새 구간 데이터가 들어오면 파티션을 알아서 만들어준다. 손댈 일이 없다.
  • MariaDB/MySQL엔 그런 자동 생성이 없다. 찾아보니 정말 없더라.. 미리 만들어두거나, 주기적으로 ADD PARTITION 해주거나 둘 중 하나다.

그래서 방법이 갈린다.

  1. 크론으로 주기적 ADD PARTITION — “다음 구간 파티션이 없으면 추가"하는 잡을 돌리는 것. 유연하지만, 이 잡이 조용히 실패하면 어느 날 담을 파티션이 없어서 터진다. 운영 의존성이 하나 늘어난다.
  2. 설치 시점에 미리 통째로 생성 — 빈 테이블을 만들 때 앞으로 쓸 파티션을 한꺼번에 다 만들어두는 것.

나는 새 장비를 설치하고 DB를 처음 만들 때 20년치 파티션을 미리 생성하는 쪽을 택했다. 구간은 데이터가 쌓이는 양에 맞춰 3개월/6개월/1년 중에 골라 잡고. 근거는 이렇다.

  • 장비 자체가 보통 10년쯤이면 교체된다. 20년치면 수명 내내 파티션이 모자랄 일이 없다.
  • 파티션 생성을 빈 테이블에, 설치 시점에 하니까 — 데이터도 트래픽도 없는 상태라 — 그 위험한 라이브 재구성을 영영 안 하게 된다. 운영 중 ALTER가 아예 사라지는 게 핵심이다.
  • 빈 파티션은 거의 공짜다. MySQL/MariaDB는 파티션을 수천 개까지 허용하고(상한 8192개), 비어 있는 파티션은 사실상 메타데이터뿐이라 수십 개 미리 깔아둬도 부담이 없다.

이게 “정석"인지는 솔직히 나도 모른다. 크론으로 굴리는 게 더 우아하다고 볼 사람도 있을 거다. 다만 현장에 설치돼서 유지보수 손이 잘 안 닿는 장비라면, 매달 도는 잡 하나에 목숨 거는 것보다 설치할 때 20년치 깔아두고 잊는 쪽이 사고 날 여지가 적다고 판단했다. 운영 중 재구성으로 테이블을 깨먹어 본 입장에선, 이 트레이드오프가 납득이 됐다.

정리#

  • 파티션 키는 모든 PK/UNIQUE에 포함돼야 한다 — 규칙은 사실상 이거 하나.
  • seq냐 날짜냐는 **“무엇으로 지울 거냐”**로 정한다. 보관정책 있으면 날짜.
  • auto_increment PK 전환은 DROP+ADD를 한 ALTER에 묶고, PK 컬럼은 NOT NULL.
  • FK 미지원, DDL은 롤백 불가, 그리고 운영 중 라이브 재구성은 테이블을 깨먹을 수 있다 — 이 셋은 미리 모르면 크게 덴다. 접근을 끊고 하거나, 아예 설치 시점에 미리 만들어 재구성을 피한다.
  • MariaDB엔 자동 파티셔닝이 없어서, 나는 설치 때 20년치를 미리 생성해 운영 중 ALTER를 없앴다.
  • 핵심 보상은 DROP PARTITION으로 즉시 구간 삭제.

파티셔닝은 “쿼리 빨라지는 마법"이라기보단, 오래된 데이터를 값싸게 버릴 수 있게 해주는 구조 정리에 가까웠다. 조회 성능은 파티션 키로 필터링할 때(파티션 프루닝)만 덤으로 붙는다. 그리고 무엇보다 — 생각보다 위험한 작업이다. 운영 중인 테이블을 건드리는 순간 리스크가 확 올라가니, 가능하면 처음 만들 때 구조를 잡아두는 게 제일 마음 편했다.
