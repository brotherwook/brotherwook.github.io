문제: 느린 DB 조회가 파이프라인을 붙잡는다#

두 모듈이 하나의 파이프라인으로 이어지는 상황이 있었다. 앞 모듈(선행 모듈)이 어떤 작업을 마치면 그 결과로 DB에서 무언가를 조회할 key를 만들어내고, 뒤 모듈(내 모듈)이 그 key로 DB를 조회해서 후속 처리를 한다.

문제는 이 DB 조회가 느리다는 것이었다. 데이터가 잔뜩 쌓인 테이블에서 큰 바이너리(이미지 blob 같은)를 꺼내와야 했고, 한 건당 시간이 제법 걸렸다. 두 모듈을 그냥 함수 호출로 직결하면, 앞 모듈은 뒤 모듈의 느린 조회가 끝날 때까지 매번 기다려야 한다. 앞 모듈도 나름 추론 등 할 일이 있는데 뒤 모듈의 I/O에 발이 묶이는 것.

핵심 요구는 이랬다. 두 모듈을 떼어내서, 앞은 앞대로 빠르게 일하고 뒤는 자기 페이스로 밀린 조회를 처리하게 만들자. 이걸 위해 사이에 Redis List 기반 작업 큐를 끼웠다.

왜 Redis 큐였나#

선택 이유는 세 가지였다.

1) 비동기 분리 — 앞 모듈은 “이 key 처리해줘"를 큐에 던지기만 하고 바로 자기 일로 돌아간다. 뒤 모듈은 큐에서 하나씩 꺼내 느린 DB 조회를 처리한다. 생산 속도와 소비 속도가 달라도 큐가 완충 역할을 하니 서로를 기다리지 않는다.

2) 프로세스·모듈 결합도 감소 — 두 모듈이 서로의 함수 시그니처나 내부 구현을 알 필요가 없다. 오직 “큐에 어떤 형식의 메시지가 흐른다"는 계약만 공유한다. 한쪽을 재시작하거나 교체해도 다른 쪽은 영향을 덜 받는다. 심지어 두 모듈이 다른 언어·다른 프로세스여도 Redis를 사이에 두면 통신이 된다.

3) 부하 분산의 발판 — 뒤에서 설명하겠지만, 조회를 처리하는 워커를 여러 서버로 늘리고 큐를 매개로 일을 나눠 갖게 만들 수 있다. 처음부터 이걸 염두에 두고 큐를 골랐다.

솔직히 “제대로 하려면 RabbitMQ나 Kafka 같은 메시지 브로커를 봐야 하나” 싶기도 했는데.. 이번 요구엔 그 정도까진 필요 없었고, 이미 쓰고 있던 Redis로 충분했다. Redis의 List가 이 용도에 잘 맞는다. LPUSH/RPUSH로 넣고 LPOP/RPOP으로 꺼내며, 양끝 어디로든 넣고 뺄 수 있어서 큐(FIFO)로도 스택(LIFO)으로도 쓸 수 있다. 이 유연함이 뒤에 나올 설계에 그대로 쓰였다.

기본 구조: 프로듀서 / 컨슈머#

가장 단순한 형태는 이렇다.

# 프로듀서 (선행 모듈): 처리할 key를 큐에 넣는다
r.lpush("task:main", json.dumps({"key": db_key, "meta": ...}))

# 컨슈머 (내 모듈): 큐에서 꺼내 느린 DB 조회를 처리한다
while True:
    item = r.rpop("task:main")
    if item is None:
        time.sleep(polling_interval)   # 비어 있으면 잠깐 쉬고 다시
        continue
    task = json.loads(item)
    process(task)   # 여기서 느린 DB 조회 + 후속 처리

LPUSH로 넣고 RPOP으로 꺼내면 먼저 들어온 게 먼저 나가는 FIFO 큐가 된다. 앞 모듈은 큐에 던지고 즉시 복귀, 뒤 모듈은 밀린 일을 자기 속도로 소진한다.

참고: 폴링 대신 BRPOP(블로킹 pop)을 쓰면 큐가 빌 때 CPU를 덜 쓰면서 새 작업을 기다릴 수 있다. 타임아웃을 줘서 주기적으로 깨어나 다른 일(종료 신호 확인 등)을 하게 하는 구성도 가능하다. 나는 처리 중 다른 상태도 봐야 해서 폴링으로 뒀지만, 순수하게 큐만 소비하면 BRPOP이 낫다.

설계 1: FIFO / LIFO를 설정으로 전환#

작업을 오래된 것부터 처리할지, 최신 것부터 처리할지는 상황에 따라 다르다.

  • 밀린 작업을 공평하게 순서대로 비우고 싶으면 FIFO(오래된 것 우선)
  • 최신 상태가 더 중요하고 오래된 건 가치가 떨어지는 성격이면 LIFO(최신 우선)

Redis List에서는 이게 꺼내는 쪽 방향만 바꾸면 되는 문제다. LPUSH로 넣는다고 할 때:

  • RPOP → 반대쪽 끝에서 꺼냄 → FIFO
  • LPOP → 넣은 쪽 끝에서 꺼냄 → LIFO

그래서 이 방향을 JSON 설정 파일로 바꿀 수 있게 만들었다. 코드를 고치지 않고 운영 중에 정책을 선택할 수 있게.

1
2
3

# config.json 의 값에 따라 pop 방향 결정
pop = r.lpop if config["main_queue_order"] == "lifo" else r.rpop
item = pop("task:main")

작은 장치지만, “이 큐를 어떤 순서로 비울 것인가"를 배포 없이 운영 판단으로 넘길 수 있어 꽤 유용했다.

설계 2: 에러 전용 재시도 큐 (최신 실패 우선)#

느린 DB 조회는 실패할 수 있다. 일시적인 커넥션 문제, 락, 타임아웃 등. 실패한 작업을 그냥 버리면 유실이고, 그렇다고 같은 큐 맨 뒤에 다시 넣으면 정상 흐름과 뒤섞인다.

그래서 에러 전용 큐를 따로 뒀다.

1
2
3
4
5
6

try:
    task = pop("task:main")
    process(task)
except Exception as e:
    logger.warning(f"처리 실패, 재시도 큐로: {e}")
    r.lpush("task:retry", item)   # 실패분은 재시도 큐로

재시도 큐는 나(컨슈머) 혼자만 쓰는 큐다. 프로듀서는 이 큐를 모른다. 그리고 재시도는 LPUSH + LPOP 조합으로 LIFO — 즉 방금 실패한 게 가장 먼저 다시 시도되는 구조로 설계했다.

1
2

# 재시도 처리: 최근 실패분부터
retry_item = r.lpop("task:retry")

왜 최신 실패 우선(LIFO)로 의도했나. 실패가 몰릴 때 오래된 실패부터 붙잡고 있으면 방금 들어온 작업이 오래 지연된다. 최신 실패를 먼저 재시도하면 “지금 막 문제된 것"을 빠르게 회복시킬 수 있고, 정말 고질적으로 안 되는 것들은 뒤로 밀려 자연스럽게 후순위가 된다. 정상 큐(FIFO/LIFO 전환 가능)와 재시도 큐(LIFO 고정)의 처리 방향이 서로 다른 것이 이 설계의 특징이다.

정리하면 두 큐의 역할이 이렇게 나뉜다.

큐넣기꺼내기순서쓰는 주체
메인 큐프로듀서가 LPUSHRPOP/LPOP (설정)FIFO/LIFO 선택프로듀서 → 컨슈머
재시도 큐컨슈머가 LPUSH컨슈머가 LPOPLIFO컨슈머 단독

설계 3: 여러 서버로 부하 분산 — 짧은 큐에 넣기#

처리량을 더 높이려면 조회 워커를 여러 서버로 늘려야 한다. 이때 “어느 서버에 일을 줄까"를 정하는 방법이 필요하다.

간단하면서 효과적이었던 방식은, 프로듀서가 작업을 넣을 때 각 서버 큐의 현재 길이를 보고, 가장 짧은 큐에 넣는 것이다. LLEN으로 길이를 조회할 수 있다.

1
2
3
4

# 여러 워커 서버의 큐 중 가장 짧은 곳에 작업을 넣는다
queues = ["task:main:w1", "task:main:w2", "task:main:w3"]
target = min(queues, key=lambda q: r.llen(q))
r.lpush(target, payload)

이렇게 하면 처리 속도가 빠른(=큐가 빨리 비는) 서버에 자연스럽게 더 많은 일이 몰리고, 느린 서버엔 덜 간다. 라운드로빈처럼 기계적으로 나누는 것보다 실제 처리 여력에 비례해서 일이 분배되는 효과가 있다. 별도 로드밸런서 없이 큐 길이라는 단순한 신호만으로 부하 분산이 되는 셈이다.

주의: LLEN으로 보고 LPUSH로 넣는 사이에 다른 프로듀서가 끼어드는 레이스가 이론적으로 있다. 프로듀서가 하나이거나, 분배가 완벽히 균등할 필요는 없는 상황(대략 짧은 쪽으로 쏠리기만 하면 충분)에서는 이 단순한 방식으로도 잘 동작했다. 더 엄격해야 한다면 Lua 스크립트로 조회+삽입을 원자적으로 묶는 방법이 있다.

테스트 모드: 큐를 비우지 않고 들여다보기#

개발·디버깅 중엔 큐에서 작업을 꺼내(pop) 소비해버리면 곤란할 때가 있다. 실제로 지우지 않고 내용만 확인하고 싶은 것. 이럴 땐 pop 대신 비파괴적으로 조회하면 된다.

  • 특정 인덱스만 보기: LINDEX key 0 (맨 앞 항목)
  • 범위로 훑기: LRANGE key 0 9 (앞 10개)

테스트 모드에서는 이렇게 “꺼내지 않고 보기"로 동작을 검증하고, 실제 모드에서만 RPOP/LPOP으로 소비하도록 분기해두면, 큐 내용을 망가뜨리지 않고 파이프라인을 점검할 수 있다. 이 작은 분기 하나가 디버깅할 때 은근히 큰 도움이 됐다.

정리#

느린 DB 조회 하나 때문에 시작한 일이었는데, Redis List를 큐로 쓰면서 얻은 게 많았다.

  • 비동기 분리: 프로듀서는 던지고 복귀, 컨슈머는 자기 페이스로 소비. 서로의 속도에 묶이지 않는다.
  • 결합도 감소: 두 모듈은 “큐에 흐르는 메시지 형식"만 공유한다. 구현·언어·생명주기가 독립적이다.
  • List의 양방향성으로 FIFO/LIFO를 자유롭게 구성 — 메인 큐는 설정으로 전환, 재시도 큐는 최신 실패 우선(LIFO)로 고정.
  • 에러 전용 재시도 큐로 실패 작업을 유실 없이, 정상 흐름과 분리해 처리.
  • 큐 길이 기반 분배로 별도 로드밸런서 없이 여러 워커 서버에 부하를 나눔.

거창한 메시지 브로커를 도입하지 않고 Redis List만으로도 이 정도 비동기 파이프라인이 나온다. “느려서 못 기다리겠다"는 문제를 만났을 때, 모듈 사이에 큐 하나 끼우는 것만으로 구조가 얼마나 유연해지는지를 배운 작업이었다. 물론 트래픽이 더 커지거나 메시지 보장이 중요해지면 그땐 전용 브로커를 봐야겠지만.. 지금 규모엔 이게 딱 맞았다.
