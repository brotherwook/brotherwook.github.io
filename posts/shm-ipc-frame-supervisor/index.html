[Python] 공유메모리로 영상 프레임 넘기고, 죽으면 되살리기 — shm IPC와 감독 패턴

프레임을 어떻게 넘길까#

영상을 다루다 보면 프로세스가 자연스럽게 둘로 갈린다. 한쪽은 영상을 받아 디코딩해서 프레임을 뽑는 쪽(생산자), 다른 한쪽은 그 프레임으로 뭔가 처리하는 쪽(소비자 — 객체 검출이든 저장이든). 문제는 이 둘 사이로 매초 수십 장의 이미지 프레임이 오가야 한다는 것이다.

이걸 소켓이나 파일로 넘기면.. 프레임 하나가 수 MB인데 그걸 계속 직렬화해서 복사하면 CPU도 대역폭도 아깝다. 그래서 꺼낸 게 **공유메모리(shared memory)**다. 메모리 한 구역을 두 프로세스가 같이 들여다보면 복사 없이 프레임을 넘길 수 있다. 리눅스에선 /dev/shm 위에 얹힌다.

이 구조 자체는 잘 도는데, “소비자가 죽었다"를 감지하고 되살리는 부분에서 예상 못 한 함정을 여럿 만났다. 그 기록이다.

공유메모리로 프레임 공유하기#

파이썬이면 표준 라이브러리 multiprocessing.shared_memory로 된다. 생산자가 세그먼트를 만들고(create), 소비자는 이름으로 붙는다(attach). numpy 배열을 그 위에 얹으면 프레임을 바로 읽고 쓸 수 있다.

from multiprocessing import shared_memory
import numpy as np

H, W, C = 1080, 1920, 3
NAME = "frame_ch1"

# 생산자: 세그먼트 생성 후 프레임을 계속 덮어씀
shm = shared_memory.SharedMemory(name=NAME, create=True, size=H*W*C)
buf = np.ndarray((H, W, C), dtype=np.uint8, buffer=shm.buf)
buf[:] = frame            # 디코딩한 프레임을 복사 없이 게시

# 소비자: 이름으로 붙어서 읽기
shm = shared_memory.SharedMemory(name=NAME)          # create=False
buf = np.ndarray((H, W, C), dtype=np.uint8, buffer=shm.buf)
frame = buf.copy()        # 필요하면 스냅샷

실제로는 “지금 프레임이 갱신됐는지"를 알려주는 프레임 카운터나 락/세마포어를 하나 더 두는 게 보통이지만, 핵심은 생산자가 만들고 소비자가 붙는다는 것이다. 그리고 바로 여기서 문제가 시작된다.

소비자가 죽는 건 대부분 “생산자가 없어서"다#

소비자를 켰는데 이런 식으로 바로 죽는 경우가 있다.

1

FileNotFoundError: No shared memory block associated with name 'frame_ch1'

create=False로 붙으려는데 그 이름의 세그먼트가 아직 없다는 뜻이다. 즉 생산자가 아직 안 떴거나, 떴다가 죽어서 세그먼트가 사라진 것. 소비자 잘못이 아니라 생산자가 준비가 안 된 것이다.

이걸 제대로 이해 못 하면 다음 함정에 그대로 빠진다.

함정: “재시작해도 계속 죽는다”#

소비자가 죽으면 감독(supervisor) 프로세스가 되살리게 해뒀다. 그런데 로그를 보면 소비자가 안 켜지는 것처럼 보였다. 감독이 분명 재시작을 시도하는데도.

원인은 단순했다. 생산자가 여전히 죽어있으면, 소비자를 아무리 재시작해도 붙을 shm이 없어서 똑같이 1초 만에 다시 죽는다. 감독은 열심히 재시작을 “시도"하고 있지만, 육안으로는 계속 꺼져 있는 것처럼 보인다. 즉 상황은 **“안 켜진다"가 아니라 “계속 즉시 재실패하는 중”**이었다.

교훈이 두 개다.

  • 재시작은 근본 원인부터. 소비자를 되살리기 전에 생산자(shm을 만들어주는 쪽)가 살아있는지부터 확인해야 한다. 안 그러면 무한 재실패 루프다.
  • 로그를 “시도"와 “성공"으로 구분해서 남겨야 한다. “재시작 시도 N회"가 찍히고 있으면 감독은 정상이고 원인은 딴 데(생산자) 있는 것이다. 이 구분이 없으면 “감독이 고장 났나?“를 엉뚱하게 파게 된다.

함정: grace 타임과 폴링 주기가 겹치면 느려 보인다#

또 하나. 감독이 30초마다 상태를 폴링하면서, 재시작에는 grace time(예: 60초) — “방금 재시작했으니 60초는 다시 안 건드림” — 을 뒀었다. 그런데 소비자가 shm이 없어서 1초 만에 죽어도, 이 grace 60초는 그대로 카운트된다.

결과적으로 30초 폴링 중 절반은 grace에 걸려 스킵되고, 실제 재시작은 약 60초에 한 번씩만 일어났다. “왜 이렇게 느리게 되살아나지?” 싶었는데, 죽는 건 즉시인데 되살리는 주기가 grace에 묶여 있던 것이다. 재시작 실패가 즉시라면 grace를 실패에는 짧게, 성공에만 길게 두는 식으로 분리하는 게 맞았다.

죽음을 어떻게 전파할까#

소비자 내부에서 프레임 읽는 스레드가 죽었을 때, 그걸 감독에게 알리는 흐름은 이렇게 잡았다.

  1. main 루프가 1초마다 thread.is_alive()로 워커 스레드 생사를 감시
  2. 죽은 게 감지되면 상태를 error로 바꾸고 전체 정리(cleanup) 후 종료
  3. 소비자는 감독과 소켓으로 연결돼 있는데, 종료하며 소켓을 닫으면 감독 쪽이 EOF를 감지해서 “이 워커 죽었다"로 표시
  4. 감독의 폴링 루프가 그 상태를 보고 재시작

소켓 EOF로 죽음을 전파하는 게 은근 깔끔하다. 프로세스가 어떤 이유로 죽든(정상 종료든 크래시든) 연결이 끊기니 감독이 알아챌 수 있다.

# 소비자: 워커 스레드 생사 감시
while not stop_event.is_set():
    if not worker.is_alive():
        status.set("error")
        stop_event.set()      # 나머지 정리 유도
        break
    time.sleep(1)
# 여기서 소켓을 닫으면 감독이 EOF로 감지

정리 안 하면 쌓인다#

마지막으로, 프로세스가 죽을 때 자기 흔적을 명시적으로 정리하게 해야 한다. 안 그러면 조용히 쌓인다.

  • 생산자가 죽으면 shm.close() + shm.unlink() 로 세그먼트를 지워야 한다. 안 그러면 /dev/shm에 유령 세그먼트가 남는다.
  • “실행 중” 표시용으로 쓰는 pid 파일(is_running_* 같은) 이 있으면, 죽을 때 지우는 로직의 파일명 패턴이 실제와 맞는지 확인. 접두사 하나 안 맞아서 정리가 안 되고 계속 쌓이는 걸 실제로 겪었다.. 이런 건 에러도 안 나서 한참 뒤에야 발견한다.

정리#

  • 프레임처럼 큰 데이터를 프로세스 간에 넘길 땐 공유메모리가 복사를 없애줘서 빠르다.
  • 소비자가 붙을 때 생산자가 세그먼트를 먼저 만들어야 한다. 없으면 즉시 죽는다.
  • 재시작은 근본 원인(생산자)부터 — 안 그러면 “재시작해도 계속 죽는” 무한 루프. 로그는 “시도"와 “성공"을 나눠 남긴다.
  • grace time과 폴링 주기의 상호작용으로 재시작이 느려 보일 수 있다. 실패에는 grace를 짧게.
  • 죽음 전파는 소켓 EOF가 깔끔하고, 죽을 땐 shm·pid 파일을 명시적으로 정리해야 쌓이지 않는다.

공유메모리 자체는 몇 줄이면 되는데, 정작 어려운 건 **“죽었을 때 어떻게 알아채고 되살리느냐”**였다. 분산도 아니고 프로세스 두 개 감독하는 건데도 이 정도라, 감독(supervisor) 로직은 처음부터 “재시작해도 안 되는 경우"를 상정하고 짜야 한다는 걸 배웠다.
