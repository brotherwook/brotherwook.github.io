[GitLab] NAS GitLab이 갑자기 403 Forbidden.. Rack::Attack 자동 밴 풀기

NAS에 Docker로 올린 GitLab이 어느 날 갑자기 403을 뱉었다. 원인은 Rack::Attack 자동 밴과 stale PID. 진단부터 복구, 재발 방지까지 정리한다.

문제 상황#

NAS에 Docker로 올려둔 GitLab이 어느 날 갑자기 접속이 안 됐다. 로그인 페이지고 뭐고 모든 페이지가 403 Forbidden을 뱉었다. 어제까지 멀쩡했는데 말이다..

일단 반사적으로 “재시작하면 되겠지” 하고 컨테이너를 재시작했다. 그런데 안 됐다. 재시작만으로 안 풀리는 문제였던 거다. 결국 로그를 까보고 나서야 원인이 두 개나 겹쳐 있었다는 걸 알았다. 이 글은 그 삽질을 정리한 기록이다.

참고로 여기서 쓰는 이미지는 sameersbn/gitlab 기반이다. Synology 같은 NAS의 GitLab 패키지가 보통 이걸 쓴다. 공식 Omnibus 이미지(gitlab/gitlab-ce)랑은 구조가 좀 달라서, gitlab-ctl 명령어가 아예 없다. 이거 모르고 컨테이너 안에 들어가서 gitlab-ctl restart 쳤다가 “command not found” 보고 당황했다..

그래서 재시작은 그냥 호스트(NAS 터미널)에서 컨테이너 통째로 하는 게 맞다.

1

docker restart synology_gitlab

1단계 - 로그부터 보자#

gitlab-ctl이 없으니 로그도 직접 찾아 들어가야 한다. 먼저 컨테이너 로그를 봤더니 이런 게 무한 반복되고 있었다.

1
2
3

INFO spawned: 'unicorn' with pid 788
INFO success: unicorn entered RUNNING state, process has stayed up for > than 1 seconds
INFO exited: unicorn (exit status 1; not expected)

unicorn은 GitLab의 웹 애플리케이션 서버다. 이게 뜨자마자 1초 만에 죽고, supervisor가 다시 살리고, 또 죽고를 무한 반복하고 있었다. 웹이 제대로 뜰 리가 없다.

exit status 1만으로는 진짜 원인이 안 보인다. 실제 에러는 unicorn 자체 로그에 찍혀 있어서, 컨테이너 안에 들어가서 두 개를 봤다.

1
2
3
4
5
6
7

docker exec -it synology_gitlab bash

# unicorn 에러 로그
cat /home/git/gitlab/log/unicorn.stderr.log | tail -50

# GitLab production 로그
tail -50 /home/git/gitlab/log/production.log

여기서 원인 두 개가 각각 튀어나왔다.

원인 A - stale PID (unicorn이 안 뜨는 이유)#

unicorn.stderr.log에 이게 계속 찍혀 있었다.

1

Already running on PID:603 (or pid=/home/git/gitlab/tmp/pids/unicorn.pid is stale) (ArgumentError)

번역하면 “이미 PID 603으로 돌고 있거나, PID 파일이 오래된 거(stale)다” 라는 뜻이다. 재시작 과정에서 unicorn이 깔끔하게 안 죽으면서 PID 파일만 남아버린 상황이다. 실제로 603번 프로세스는 없는데 파일이 남아 있으니, unicorn이 “어? 이미 누가 돌고 있네?” 하고 스스로 종료해버리는 거다.

해결은 허무할 정도로 간단하다. 죽은 PID 파일만 지우면 된다.

1

rm /home/git/gitlab/tmp/pids/unicorn.pid

원인 B - Rack::Attack 자동 밴 (403의 진짜 범인)#

production.log를 봤더니 이게 도배되고 있었다.

1
2

Rack_Attack: blacklist 172.17.0.1 GET /
Rack_Attack: blacklist 172.17.0.1 GET /favicon.ico

이게 403의 진짜 원인이었다. GitLab에는 Rack::Attack이라는 요청 차단 미들웨어가 있는데, 짧은 시간에 인증 실패(잘못된 비밀번호·토큰으로 git push/pull 시도 등)가 반복되면 그 IP를 자동으로 밴해버린다. 실제로 로그를 거슬러 올라가 보니 git-receive-pack에서 401 Unauthorized가 몇 번 나다가, 그 뒤로 전부 blacklist로 바뀌어 있었다.

여기서 이 구조의 함정이 하나 있다. NAS + Docker 환경에서는 모든 외부 요청이 172.17.0.1(Docker 브리지 네트워크의 게이트웨이) 하나로 보인다. 리버스 프록시나 NAS를 거쳐 들어오면 GitLab 입장에선 출발지 IP가 죄다 이 하나로 뭉뚱그려진다는 뜻이다.

그래서 어딘가에서 자격증명 하나가 잘못돼 인증 실패가 쌓이면, 그 IP가 밴되고 → 결과적으로 나를 포함한 모든 사용자가 403을 맞는다. NAS GitLab에서 꽤 흔하게 밟는 지뢰라고 한다.

밴 풀기#

밴 정보는 Redis에 저장된다. 이 환경에선 Redis가 별도 컨테이너(synology_gitlab_redis)로 돌고 있어서, 호스트에서 바로 접근했다.

먼저 rack attack 관련 키를 확인한다.

1

docker exec -it synology_gitlab_redis redis-cli KEYS "*rack*"

이렇게 나왔다.

1
2
3

1) "cache:gitlab:rack::attack:allow2ban:ban:172.17.0.1"
2) "cache:gitlab:exists?:myuser/myproject:267"
3) "cache:gitlab:exists?:myuser/myproject.wiki:267"

1번이 범인이다. 2, 3번은 프로젝트 존재 여부 캐시라 건드리면 안 된다. 1번만 지운다.

1

docker exec -it synology_gitlab_redis redis-cli DEL "cache:gitlab:rack::attack:allow2ban:ban:172.17.0.1"

(integer) 1이 뜨면 삭제 성공이다. 혹시 실패 카운터(count:...)가 임계치 근처에 남아 있으면 몇 번 요청에 다시 밴될 수 있으니, 아래로 한 번 더 확인해서 남은 게 있으면 같이 지워주면 된다.

1

docker exec -it synology_gitlab_redis redis-cli KEYS "*allow2ban*"

⚠️ FLUSHALL이나 FLUSHDB는 쓰지 말자. 세션·캐시까지 몽땅 날아가서 다들 로그아웃되고 캐시가 재생성된다. 데이터 손상은 아니지만 굳이 그럴 필요가 없다. *rack* / *allow2ban* 패턴만 콕 집어서 지우는 게 안전하다.

복구 순서 정리#

정리하면 이 순서로 하면 된다.

  1. 컨테이너 안에서 stale PID 삭제: rm /home/git/gitlab/tmp/pids/unicorn.pid
  2. Rack::Attack 밴 키 삭제 (위 Redis 명령)
  3. exit 후 docker restart synology_gitlab
  4. 1~3분 기다린다 (sameersbn 이미지는 부팅 때 마이그레이션 체크를 해서 완전히 뜨는 데 시간이 좀 걸린다. 재시작 직후 바로 접속하면 502가 뜨는데 정상이다..)
  5. docker logs --tail 20 synology_gitlab로 unicorn이 RUNNING 상태를 유지하는지 확인

이렇게 하니 다시 접속됐다.

재발 방지#

밴은 어디까지나 결과다. 근본은 “인증 실패가 반복됐다"는 거니까, 거기서부터 손봐야 한다.

1) 인증 실패의 원인부터 찾기 (가장 확실) 옛날 remote URL이나 저장된 자격증명으로 계속 재시도하는 클라이언트가 있는지 의심해보자. 로컬 PC, CI 스크립트, cron 스케줄러 중에 만료된 토큰이나 잘못된 계정으로 push/pull을 반복하는 놈이 범인일 확률이 높다. production.log에서 401이 어느 프로젝트·어느 요청에서 나는지 보면 범인을 특정할 수 있다.

2) 신뢰 IP 화이트리스트 (내부망 전용일 때 추천) 내부망에서만 쓰는 NAS라면, Docker 내부 대역을 Rack::Attack 화이트리스트에 넣어두면 이 자동 밴 자체가 안 걸린다. sameersbn 이미지 기준으로 컨테이너 환경변수에 추가하면 된다.

1

GITLAB_RACK_ATTACK_WHITELIST=127.0.0.1,172.17.0.0/16

추가 후 컨테이너 재생성하면 적용된다. 다만 인터넷에 노출된 GitLab이면 이건 비추다. 브루트포스 보호를 사실상 꺼버리는 셈이라, 어디까지나 내부망 전용일 때만 권한다.

3) 응급 복구 명령은 저장해두기 또 밴 걸리면 이 두 줄이면 끝난다. 어디 메모장에라도 박아두자.

1
2

docker exec synology_gitlab_redis redis-cli KEYS "*allow2ban*"
docker exec synology_gitlab_redis redis-cli DEL "해당 ban 키"

여담#

두 문제(stale PID + Rack::Attack 밴)가 하필 같이 터져서 원인 찾는 데 시간을 꽤 썼다. 재시작만으로 안 될 때는 역시 로그부터 봐야 한다는 걸 또 배웠다..

그리고 이번에 새삼 느낀 건데, NAS에 붙어 있는 GitLab 이미지가 상당히 오래된 버전인 경우가 많다. 내부망 전용이면 당장 문제는 없지만, 혹시 외부에 열려 있다면 알려진 취약점이 꽤 쌓여 있을 수 있으니 VPN 뒤에 두는 식으로 접근 제어를 한 번쯤 점검해보는 걸 추천한다.
