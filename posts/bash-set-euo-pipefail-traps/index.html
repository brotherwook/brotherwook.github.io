[Bash] set -euo pipefail 함정 — rm과 apt가 조용히 스크립트를 죽일 때

set -e 스크립트가 rm 한 줄에서 죽고, apt update는 'Done' 찍고도 스크립트를 끝내버렸다. set -e가 화면이 아니라 종료 코드만 본다는 것과, 걸리거나 안 걸리는 자리들·pipefail·set -u 함정 정리.

rm 한 줄에서 스크립트가 죽었다#

set -e가 걸린 셸 스크립트가 자꾸 특정 줄에서 멈췄다. 그 줄은 rm이었다.

원인은 단순했다. rm -f가 아니라 그냥 **rm**을 썼는데, 지울 대상이 없으면 rm은 에러(종료 코드 1)를 낸다. set -e는 그 non-zero를 보고 거기서 스크립트를 끝내버린다. 파일이 늘 있을 줄 알았는데, 어떤 실행 경로에선 없었던 것.

1
2

rm /tmp/state.lock      # 파일이 없으면 → rm: cannot remove ...: No such file or directory → exit 1 → set -e 로 종료
rm -f /tmp/state.lock   # -f 면 없어도 조용히 exit 0

해결은 -f 하나였다. rm -f(그리고 rm -rf)는 대상이 없어도 종료 코드 0이라 set -e에 안 걸린다. “없으면 그냥 넘어가기"가 목적이면 rm엔 습관적으로 -f를 붙이는 게 맞다.

여기서 원칙 하나. set -e는 첫 번째 non-zero에서 즉시 종료한다. 그러니 스크립트가 죽으면 “이 줄이 왜 non-zero를 냈지?“를 바로 확인하면 된다. 애매하면 set -x로 어디서 멈추는지, 또는 그 명령 뒤에 echo $?로 종료 코드를 찍어본다.

개별 명령을 set -e에서 빼는 법#

“이 명령은 실패해도 넘어가도 된다"를 표현하는 방법들.

1
2
3
4
5
6
7

cmd || true      # 실패해도 무시
cmd || :         # 위와 동일 (: 은 아무것도 안 하는 내장 명령)
if cmd; then ... fi   # 실패를 "조건"으로 사용 → set -e 적용 안 됨

# 파일/디렉토리 존재를 먼저 가드하는 게 의도가 더 분명할 때가 많다
[ -d /data_temp ] && cp -a /data_temp/. /data/
rm -f /some/file      # 단일 파일 삭제는 -f 하나로 충분 (없어도 조용히 0)

“없으면 그냥 넘어가기"를 원할 땐 rm에 -f를 붙이는 것만으로 대부분 해결된다. if [ -f ... ] 가드를 굳이 또 두지 않아도 된다.

함정: “Done"이 떠도 exit 0이 아닐 수 있다#

이번에 새로 만난 것. 스크립트에서 apt update를 돌리는데, Reading package lists... Done까지 멀쩡히 찍히고선 그 뒤 단계로 안 넘어가고 스크립트가 끝나버렸다. “다 됐는데 왜 여기서 끝나지?” 하고 한참 봤다.

범인은 apt update 자체였다. 화면엔 성공처럼 보여도, 저장소 하나가 접근이 안 되거나 GPG 경고(W: ...) 같은 게 끼면 apt는 종료 코드를 non-zero로 낸다. set -e는 출력이 아니라 종료 코드만 보므로, “Done” 뒤에서 조용히 중단된 것.

교훈은 앞과 같다 — 화면상 성공 ≠ exit 0. 죽는 지점이 애매하면 그 명령 뒤에 echo $?를 찍어 실제 종료 코드부터 확인한다.

1
2
3

apt-get update            # 저장소 경고/일부 실패 시 non-zero → set -e 로 중단
apt-get update || true    # 경고를 무시하고 계속하려면
# 스크립트에선 apt 보다 apt-get 을 쓰는 게 CLI 안정성 면에서 낫다

함정: set -e가 “안 걸리는” 자리들#

반대로, 실패해도 스크립트가 안 죽는 맥락이 있다. 이걸 모르면 “왜 이 실패는 그냥 지나가지?” 하고 헤맨다. set -e는 다음 위치의 실패를 무시한다.

  • if, while, until 조건에 쓰인 명령
  • &&, ||의 좌변에 있는 명령 (cmd1 && cmd2에서 cmd1)
  • !로 부정한 명령
  • 함수가 위 조건 자리에서 호출될 때 — 그 함수 안의 실패도 통째로 무시된다 (이게 특히 함정)

즉 check_something && do_next 처럼 써두면, check_something 안에서 뭐가 터져도 set -e가 안 잡아준다.

함정: pipefail 없으면 파이프 중간 실패가 숨는다#

set -e만 켜면 파이프라인은 마지막 명령의 종료 코드만 본다. 중간이 실패해도 마지막이 성공하면 전체가 성공으로 친다.

1
2
3

set -e
grep something big.log | sort > out.txt
# grep 이 실패(예: 파일 없음)해도, sort 가 성공하면 스크립트는 안 죽는다

그래서 set -o pipefail을 같이 켜서 파이프 중 하나라도 실패하면 실패로 잡는다.

그런데 여기 반대 함정이 있다. set -e + pipefail을 켠 상태에서 grep이 매칭을 하나도 못 찾으면 종료 코드 1을 낸다. 이건 “에러"가 아니라 “결과 없음"인데도 스크립트가 거기서 죽어버린다.

1
2
3

set -eo pipefail
count=$(grep -c ERROR app.log)   # ERROR 가 하나도 없으면 grep 이 1 → 스크립트 종료(!)
count=$(grep -c ERROR app.log || true)   # 이렇게 방어

“매칭 없음"을 정상으로 봐야 하는 grep은 || true로 감싸는 습관을 들이는 게 좋다.

함정: set -u 와 빈 변수#

set -u는 설정 안 된 변수를 쓰면 에러를 낸다. 오타나 인자 누락을 잡아줘서 좋지만, “없을 수도 있는 값"엔 기본값을 줘야 한다.

1
2
3
4

set -u
echo "$UNDEFINED"        # 에러 → 종료
echo "${UNDEFINED:-기본}" # 안전
echo "${1:-}"            # 인자가 없을 수 있으면 이렇게

함정: local 이 exit 코드를 덮는다#

이건 알기 전엔 절대 못 잡는다. 함수 안에서 local x=$(cmd)로 쓰면, local 자체가 성공(0)을 반환하기 때문에 cmd가 실패해도 그 종료 코드가 덮여서 set -e가 못 잡는다.

1
2
3
4
5
6
7
8
9

foo() {
    local x=$(might_fail)    # might_fail 이 실패해도 local 이 0 → set -e 안 걸림
    # ...
}

foo() {
    local x                  # 선언과
    x=$(might_fail)          # 대입을 분리하면 might_fail 의 실패가 살아난다
}

정리#

스크립트 맨 위에 set -euo pipefail을 깔되, 각각이 언제 “안 걸리는지"까지 알아야 진짜 방어가 된다.

  • set -e는 첫 non-zero에서 즉시 종료 — 죽으면 그 줄이 낸 종료 코드를 echo $?/set -x로 확인.
  • 그냥 rm은 대상 없으면 exit 1 → rm -f/rm -rf로. (-f면 없어도 exit 0)
  • 화면상 성공 ≠ exit 0 — apt update처럼 “Done” 찍고도 non-zero를 내는 명령이 있다. 계속하려면 || true.
  • 개별 면제는 || true, || :, if cmd; then, 존재 가드로.
  • if·&&/||·함수 조건 자리의 실패는 set -e가 안 잡는다.
  • pipefail 없으면 파이프 중간 실패가 숨고, 있으면 **매칭 없는 grep(exit 1)**에 물리니 || true.
  • set -u엔 ${VAR:-기본}, local x=$(cmd)는 선언·대입 분리.

set -euo pipefail은 켜두면 안심되는 주문 같지만, 사실은 “어디서 걸리고 어디서 안 걸리는지"를 알아야 쓸모가 있는 도구였다. rm 한 줄에 멈추고, apt update가 “Done"까지 찍고도 스크립트를 끝내는 걸 겪고 나서야, set -e가 보는 건 화면이 아니라 종료 코드라는 걸 몸에 새겼다.
