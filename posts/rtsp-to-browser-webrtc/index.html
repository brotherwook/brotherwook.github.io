문제: RTSP는 브라우저가 못 읽는다#

앞 글에서 IP 카메라의 RTSP 스트림을 받아오는 데는 성공했다. 이제 이걸 웹 화면에서 실시간으로 보여주고 싶었다. 관리자용 CMS든 모니터링 대시보드든, 결국 사용자는 브라우저에서 영상을 본다.

처음엔 순진하게 이렇게 생각했다.

1

<video src="rtsp://.../stream" controls></video>

안 된다. 브라우저의 <video> 태그는 RTSP를 지원하지 않는다. HTTP(S)로 서빙되는 MP4나, HLS/DASH 같은 HTTP 기반 스트리밍, 아니면 WebRTC로만 영상을 받을 수 있다. RTSP는 태생이 브라우저용이 아니다.. 그래서 RTSP를 브라우저가 알아듣는 형식으로 중간에서 변환해주는 서버가 반드시 필요하다.

여기서부터 “그럼 뭘로 변환하지?“라는 선택의 문제가 시작됐다.

시도 1: HLS — 되긴 되는데 느리다#

제일 먼저 손이 간 건 HLS(HTTP Live Streaming)였다. 자료도 많고 원리도 단순하다. 영상을 몇 초짜리 조각(segment)으로 잘라 .ts/.m4s로 만들고, 재생목록(.m3u8)을 통해 브라우저가 순서대로 받아 재생한다. HTTP 기반이라 방화벽·CDN 친화적이고 안정적이다.

문제는 **지연(latency)**이었다.

HLS는 구조적으로 세그먼트를 만들고 → 여러 개 쌓은 뒤 → 재생목록에 올려야 브라우저가 받아간다. 이 과정에서 보통 수 초에서 십수 초 지연이 생긴다. VOD나 라이브 방송이면 괜찮은데, CCTV 모니터링처럼 “지금 이 순간"을 봐야 하는 용도엔 치명적이다. 게이트 앞에 누가 서 있는지를 10초 늦게 보는 건 실시간이라 부르기 어렵다.

Low-Latency HLS(LL-HLS)로 줄일 수는 있지만 설정이 까다롭고, 그렇게까지 해도 WebRTC의 지연을 따라오긴 어렵다. “실시간"이 핵심 요구라면 방향을 바꿔야 했다. 개인적으로 실시간이 아니어도 되는 용도면 HLS가 훨씬 편하다. 실시간이 진짜 필요할 때만 아래로 넘어가는 걸 추천한다.

시도 2: WebRTC — 진짜 실시간, 대신 개념의 벽#

실시간 저지연이 필요하면 결국 WebRTC다. 원래 화상회의용으로 만들어진 기술이라 1초 미만 지연을 목표로 하고, 브라우저에 기본 내장돼 있어 플러그인도 필요 없다.

그런데 WebRTC는 “쉽게 되는” 기술이 아니었다. HLS가 “파일을 HTTP로 주는” 단순한 모델이었다면, WebRTC는 두 피어(peer)가 서로를 찾아 직접 연결을 맺는 훨씬 복잡한 모델이다. 여기서 처음 듣는 개념들이 쏟아졌다.. 솔직히 이 부분은 지금도 완벽히 안다고는 못 하겠고, 내가 이해한 만큼만 적어둔다.

ICE, STUN, TURN이 뭔가#

WebRTC 연결을 이해하려면 이 셋은 알아야 했다.

  • ICE (Interactive Connectivity Establishment) — 두 피어가 연결 가능한 경로(후보, candidate)를 여러 개 모으고, 그중 실제로 통하는 길을 찾아내는 프레임워크. “어떻게든 서로 닿는 길을 찾는” 전체 절차라고 보면 된다.
  • STUN (Session Traversal Utilities for NAT) — 대부분의 기기는 공유기(NAT) 뒤에 있어서 자기 공인 IP를 모른다. STUN 서버가 “네가 밖에서 보이는 주소는 이거야"라고 알려준다. NAT 뒤 피어들이 서로의 실제 주소를 알아내 직접 연결(P2P)하게 돕는다.
  • TURN (Traversal Using Relays around NAT) — STUN으로도 직접 연결이 안 되는 까다로운 네트워크(대칭형 NAT 등)에서는 TURN 서버가 **중계(relay)**를 해준다. P2P가 실패했을 때의 우회로다.

이 개념들을 모르고 예제 코드만 따라 하면 “로컬에선 되는데 다른 네트워크에선 연결이 안 되는” 상황에 부딪힌다. 나도 그랬다.. 원인이 NAT traversal이라는 걸 이해하고 나서야 왜 STUN이 필요한지 납득이 됐다.

찾아보니 coturn이라는 오픈소스로 STUN/TURN 서버를 직접 띄울 수 있었다. 공개 STUN 서버를 쓸 수도 있지만, 폐쇄망이나 자체 인프라에서는 coturn으로 직접 운영하는 게 안정적이다.

시그널링(핸드셰이크)은 WebRTC에 안 들어있다#

제일 헷갈렸던 부분. WebRTC 연결은 시작 전에 두 피어가 서로의 정보를 교환해야 한다. 이걸 시그널링(signaling)이라 한다.

  • 한쪽이 Offer(SDP: 내가 지원하는 코덱, 미디어 정보 등)를 만들어 보낸다
  • 상대가 Answer(SDP)로 응답한다
  • 양쪽이 모은 ICE candidate(연결 후보 경로)를 주고받는다

여기서 결정적으로 막혔던 건, 이 교환을 WebRTC가 대신 해주지 않는다는 점이었다. WebRTC 표준은 “무엇을 교환할지"만 정하고, “어떻게 전달할지"는 개발자에게 맡긴다. 그래서 Offer/Answer/candidate를 실어 나를 별도 통신 채널(WebSocket, HTTP 등)을 직접 만들어야 한다. “핸드셰이킹이 안 된다"고 헤맸던 이유가 이거였다.. 연결을 맺어주는 시그널링 경로 자체를 내가 마련해야 하는 줄 몰랐던 것.

이 구조를 이해하고 나니 흐름이 정리됐다.

피어 A ──(Offer/SDP)──> [시그널링 서버] ──> 피어 B
피어 A <──(Answer/SDP)── [시그널링 서버] <── 피어 B
피어 A <──(ICE candidates)──> [시그널링 서버] <──> 피어 B
   │                                               │
   └──────── (STUN으로 경로 확인 후) 직접 미디어 연결 ────────┘

직접 다 만들 필요는 없었다: MediaMTX 같은 변환 서버#

여기까지 오면 “RTSP 받기 + WebRTC 변환 + 시그널링 + STUN"을 전부 직접 짜야 하나 싶어 아득해진다. 다행히 이 파이프라인을 상당 부분 해결해주는 오픈소스 미디어 서버들이 있다. 대표적인 게 MediaMTX다.

MediaMTX 같은 서버가 하는 일을 정리하면:

  • 입력으로 RTSP/RTMP 등 다양한 프로토콜 스트림을 받아들이고
  • 출력으로 같은 스트림을 RTSP, HLS, WebRTC 등 여러 형식으로 동시에 내보내고
  • WebRTC 재생에 필요한 시그널링 엔드포인트를 자체 제공한다

즉 “카메라의 RTSP를 받아서, 브라우저가 WebRTC로 바로 붙을 수 있게” 중간 변환을 담당한다. 덕분에 저수준 변환을 매번 직접 짜는 대신, 이런 서버를 파이프라인의 변환 계층으로 두는 선택이 가능해진다. 나처럼 “실시간 재생이 목표지 WebRTC 구현 자체가 목표는 아닌” 경우라면, 이걸 먼저 검토해보길 추천한다.

전체 파이프라인: 카메라 → 서버 → 브라우저#

[IP 카메라]
   │  RTSP (필요시 TLS로 암호화)
   ▼
[미디어 서버 (예: MediaMTX)]
   │  - RTSP 입력을 수신
   │  - WebRTC로 변환, 시그널링 제공
   │  - (STUN/TURN 연동으로 NAT 통과)
   ▼
[브라우저]
   - WebRTC로 접속
   - <video> 요소에 실시간 스트림 재생 (1초 미만 지연)
  • 카메라 → 서버: RTSP로 영상을 끌어온다. 보안이 필요하면 앞 글처럼 TLS로 감싼다.
  • 서버: 프로토콜 변환의 핵심. RTSP를 브라우저 친화적인 WebRTC로 바꾸고, 연결 협상(시그널링)과 NAT 통과(STUN/TURN)를 처리한다.
  • 서버 → 브라우저: 브라우저는 WebRTC로 붙어 저지연 재생. 이제야 <video>에 실시간 영상이 뜬다.

정리하며#

브라우저에서 RTSP를 실시간으로 보여주는 일은 “태그에 URL만 넣으면 되겠지"에서 시작해 프로토콜 변환의 세계로 끌려 들어가는 여정이었다. 배운 걸 압축하면:

  • 브라우저는 RTSP를 직접 못 읽는다. 중간 변환 서버가 반드시 필요하다.
  • HLS는 안정적이고 자료가 많지만 구조적 지연 때문에 실시간 감시엔 부적합하다.
  • WebRTC는 저지연 실시간에 강하지만, **ICE/STUN/TURN(NAT 통과)**과 시그널링(Offer/Answer/candidate 교환) 개념을 이해해야 한다. 특히 시그널링 경로는 개발자가 직접 마련해야 한다.
  • MediaMTX 같은 미디어 서버를 쓰면 이 변환·시그널링 상당 부분을 위임할 수 있어 파이프라인을 훨씬 현실적으로 구성할 수 있다.

프로토콜 하나를 브라우저에 얹는 일이 이렇게 많은 개념을 요구할 줄은 몰랐다.. 그래도 덕분에 실시간 스트리밍이 어떤 조각들로 이뤄지는지 전체 그림을 얻었다. 다음에 비슷한 요구가 오면 이제 어디서부터 손대야 할지는 안다.
