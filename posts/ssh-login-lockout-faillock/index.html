[Linux] SSH 로그인 실패 잠금, common-auth 말고 faillock.conf로

웹 UI에서 SSH 로그인 실패 잠금을 설정하는 기능을 만들다가, /etc/pam.d/common-auth 를 직접 편집하는 게 왜 위험한지 깨닫고 faillock.conf + root 래퍼 구조로 갈아엎은 기록. 포트 변경과 fail2ban 대안까지.

왜 갈아엎게 됐나#

“SSH 로그인 N번 실패하면 계정을 잠근다"는 기능을 관리용 웹 UI에서 켜고 끄게 만들어야 했다. 기존 구현을 보니 웹 서버가 /etc/pam.d/common-auth 파일을 직접 텍스트로 편집하고 있었다. 처음엔 “되긴 되네” 했는데, 뜯어볼수록 이건 그냥 두면 안 되는 코드였다.. 결국 구조를 통째로 바꿨고, 그 과정에서 배운 걸 정리한다.

common-auth를 직접 건드리면 안 되는 이유#

/etc/pam.d/common-auth를 런타임에 편집하는 방식은 문제가 한둘이 아니었다.

① common-auth는 SSH만이 아니라 모든 걸 잠근다. 이 파일은 PAM을 쓰는 모든 서비스 공통이다. 여기에 잠금을 걸면 SSH뿐 아니라 sudo, su, 콘솔 로그인, cron까지 다 영향을 받는다. “SSH만 잠그려던” 의도와 범위가 완전히 어긋난다.

② 원격에서 장비를 벽돌로 만들 수 있다. 잠금 옵션에 even_deny_root가 켜져 있으면, 누가 네트워크에서 root로 브루트포스만 해도 콘솔의 root까지 잠긴다. 즉 공격자가 로그인에 성공 못 해도 원격 DoS로 관리자를 잠가버릴 수 있다. 현장에 나가야만 풀 수 있는 상황이 원격 공격 한 번으로 만들어지는 것.

③ 낮은 권한이 이 파일을 쓸 수 있으면 그게 곧 권한 상승 통로다. 웹 서버는 보통 www-data 같은 낮은 권한으로 돈다. 그 계정이 common-auth에 쓸 수 있다는 건, 거기에 auth required pam_permit.so 한 줄만 넣으면 아무 비밀번호로나 root 로그인이 되는 문을 열 수 있다는 뜻이다. 잠금 기능을 만들려다 백도어를 만드는 격.

④ 텍스트 파싱은 깨지기 쉽다. “deny가 들어간 줄을 지운다” 같은 문자열 매칭은 표준 안전망인 auth requisite pam_deny.so 줄까지 지워버리기도 하고, 처음 켜는 장비엔 백업 파일이 없어서 해제할 때 예외로 죽기도 했다. 무엇보다 한 번 잠기면 UI에서 풀 방법이 없어서 faillock --reset을 하러 콘솔에 붙어야 했다.

제대로 된 구조 — 세 가지 원칙#

정리하고 나니 해법은 명확했다. PAM 스택 파일은 런타임에 절대 안 건드린다. 대신 이렇게 나눴다.

1) 설치할 때 딱 한 번, sshd 전용 스택에만 넣는다. common-auth가 아니라 /etc/pam.d/sshd에만 faillock 블록을 넣으면, 잠금이 SSH에만 적용된다. sudo·콘솔은 안 잠긴다.

auth  required    pam_faillock.so preauth
auth  [success=2 default=ignore]  pam_unix.so nullok
auth  [default=die] pam_faillock.so authfail
auth  sufficient  pam_faillock.so authsucc
auth  requisite   pam_deny.so
auth  required    pam_permit.so

even_deny_root는 빼는 걸 권장한다. 콘솔 복구 경로는 남겨둬야 ②번 같은 벽돌 사고를 피한다.

2) 런타임엔 숫자 두 개만 바꾼다. faillock 옵션을 줄에 안 적으면 pam_faillock이 /etc/security/faillock.conf에서 읽는다. 그래서 런타임 변경은 이 파일을 통째로 다시 쓰기만 하면 된다. 파싱도, 백업도, 복구 로직도 없다. 멱등이다.

1
2

deny = 5
unlock_time = 300

잠금 해제(off)는 deny = 0이다. pam_faillock에서 0은 “절대 잠그지 않음"이라, UI의 on/off 토글이 그대로 매핑된다. 그 지긋지긋한 .backup 복사 로직이 통째로 사라졌다.

3) 쓰기는 root 래퍼로만. 웹 앱이 직접 파일을 만지는 게 아니라, 숫자 두 개만 받아서 검증 후 파일을 쓰는 작은 root 스크립트를 두고 sudoers로 그것만 호출하게 한다. 웹 앱은 파일 경로도 내용도 못 바꾼다.

#!/bin/bash
# /usr/local/sbin/ssh-lock  (root:root 0755)  — stdin 으로 "deny unlock_time" 두 숫자만 받는다
set -u
IFS= read -r deny unlock rest
[ -n "${rest:-}" ] && { echo "인자 초과" >&2; exit 2; }
case "$deny$unlock" in *[!0-9]*) echo "숫자만" >&2; exit 3;; esac
[ "$deny" -le 10 ] && [ "$unlock" -le 3600 ] || { echo "범위 초과" >&2; exit 3; }

printf 'deny = %s\nunlock_time = %s\n' "$deny" "$unlock" > /etc/security/faillock.conf
[ "$deny" -eq 0 ] && faillock --reset   # 잠금 끄면 기존 카운터도 초기화

여기에 --reset <계정> 서브커맨드를 하나 더 두면, “잠긴 계정 풀기” 버튼을 UI에 만들 수 있다. 잠겨도 원격에서 풀 수 있게 되는 것 — 앞서 콘솔에 붙어야 했던 걸 생각하면 이게 실무에서 꽤 컸다. 잠긴 계정은 faillock --user <계정> --reset으로 푼다.

포트 변경은 “자기 발등 찍기” 조심#

로그인 잠금과 함께 SSH 포트도 자주 바꾸는데, 여기서 제일 흔한 사고가 자기 세션을 잠가버리는 것이다. 순서를 지키면 된다.

  1. sshd_config에서 Port를 바꾸기 전에, 방화벽에서 새 포트를 먼저 열어둔다. (ufw allow <새포트>/tcp 등)
  2. sshd -t로 설정 문법을 검증하고 restart.
  3. 기존 세션은 끊지 말고, 새 포트로 새 세션이 붙는지 확인한 다음에 옛 포트를 닫는다.

방화벽을 안 열고 포트만 바꾸면, restart하는 순간 새 포트는 막혀 있고 옛 포트는 닫혀서 아무도 못 들어간다. 원격 장비면 그대로 현장 출동이다.. 나는 “새 포트 열기 → 확인 → 옛 포트 닫기” 순서를 체크리스트로 박아뒀다.

대안: 계정 잠금이냐, IP 차단이냐#

방식을 고를 때 이 갈림길을 먼저 정하는 게 좋다.

  • 계정 잠금(faillock) — “N회 실패하면 그 계정을 잠근다”. 보안 요구사항 문서에 “계정 잠금"으로 못박혀 있으면 이걸 써야 한다. 단 위에서 본 것처럼 콘솔까지 잠길 위험을 설계로 막아야 한다.
  • fail2ban(IP 차단) — 계정이 아니라 공격 IP를 차단한다. 그래서 콘솔·sudo가 절대 안 잠기고, 공격자가 남의 계정을 잠가버리는 DoS도 원천 불가능하다. 운영상 제일 안전하다. 전용 설정 파일 하나(maxretry/bantime)만 두면 배포판 파일도 안 건드린다. 다만 데몬·패키지가 추가되고(오프라인 장비면 deb 번들 필요), “계정 잠금"이 요구사항이면 IP 차단으로는 대체가 안 될 수 있다.

개인적으로 요구사항이 “무단 접근 차단” 수준이면 fail2ban을, 명시적으로 “계정 잠금"이면 faillock을 쓰는 게 맞다고 본다.

참고로 sshd_config만으로 해결하려는 시도도 해봤는데 부족했다. MaxAuthTries는 한 연결당 시도 제한일 뿐 시간 잠금이 아니고, 시간 페널티를 주는 PerSourcePenalties는 OpenSSH 9.8부터라 구버전(예: 8.9)에선 못 쓴다.

정리#

  • /etc/pam.d/common-auth를 런타임에 편집하지 마라. 전 서비스에 영향 + 원격 DoS 벽돌 + 권한 상승 통로 + 파싱 취약.
  • 잠금은 설치 때 /etc/pam.d/sshd에만 한 번 넣고, 런타임엔 /etc/security/faillock.conf의 deny/unlock_time 두 숫자만 바꾼다. deny=0 = 잠금 해제.
  • 파일 쓰기는 숫자만 받는 root 래퍼 + sudoers로. --reset으로 원격에서 계정 잠금 해제까지.
  • 포트 변경은 방화벽 먼저 열고, 새 세션 확인 후 옛 포트를 닫는다.
  • 계정 잠금(faillock)과 IP 차단(fail2ban)은 목적이 다르다. 요구사항부터 정하자.

보안 기능을 만들 때 제일 무서운 건 그 기능 자체가 새 구멍을 뚫는 것이었다. “잠금을 건다"는 단순해 보이는 요구가, 잘못 구현하면 백도어이자 원격 벽돌 스위치가 될 수 있다는 걸 이번에 제대로 배웠다.
